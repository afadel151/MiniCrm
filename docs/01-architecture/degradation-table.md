# Degradation table — what still works when X is down (Phase 1)

Status: **Proposed** (Phase 1 gate). Required by CLAUDE.md §4 ("graceful degradation table per service").
Grounded in what the Phase 2 schemas actually guarantee (event-fed local read models, explicit gRPC fallbacks,
outbox durability), not aspiration — where a row says "breaks," it's because nothing in the built schema
covers it, not because no one thought about it.

| Down | Still works | Breaks / degrades | Why |
|---|---|---|---|
| **identity-access** | Already-issued, unexpired JWTs keep working at the gateway (local validation + Valkey revocation check, no live call per request); every service's cached `app.tenants`/membership read model keeps serving stale-but-usable tenant status | New logins, signups, password resets, invitations, business creation, any `CheckPermission` gRPC call (fallback = **deny**, not allow) | Gateway validates JWTs against a cached signing key, not a live call (Tech Decisions v0.2 §7.2); claims cover most permission checks already (§7.2), so `CheckPermission` is rare enough to fail closed |
| **crm** | Order placement (orders keeps its own contact/phone snapshot, reads only its own local `rm_contacts`/`rm_contact_phones`, no live call); scoring, presence, integrations all unaffected | Contact/pipeline/task UI, new contact creation, the crm timeline falls behind (messaging/orders events queue in crm's `app.inbox` undelivered-to-handler, not lost) | ADR-0002: no service calls crm synchronously on a hot path; everything crm supplies elsewhere is an event-fed read model |
| **orders** | crm contact management, scoring lookups for other reasons, presence public pages, identity-access auth — all independent | New orders, confirmation link resolution (the resolver lives in orders — a client with a link in hand gets an error until orders recovers), shipment/return processing | orders is the one context every flow in `sequence-diagrams.md` either starts in or passes through; no other service substitutes for it |
| **scoring** | Order creation **by design** — `GetScore` has a deadline + explicit fallback to `"unscored"`/default risk policy (Tech Decisions v0.2 §3.1 table) *once the gRPC client and the consumers below are actually written (Phase 5/6) — the schema and `public.lookup_score`'s gates exist and are tested today; the calling code does not yet*; crm/orders keep serving their last-cached tier (`rm_score_tiers`/`contact_score_cache`), possibly stale | New signals queue in scoring's `app.inbox` until it recovers (no data loss, just delay); merchants temporarily see no new score movement | This is the one dependency the architecture explicitly designed a fallback for from the start — the textbook case, once built |
| **integrations** | Order placement/confirmation (independent); existing shipment status stays at its last known value | New shipment creation, **carrier webhook delivery** (the carrier's own HTTP call fails/retries per the carrier's policy — unlike internal flows, nothing in MiniCrm buffers a webhook that never arrived), CSV/store imports | The outbox/inbox guarantee only covers delivery *after* an event enters our system; an external webhook that never reaches us because we were down is a gap by nature, not a bug — carriers' own retry/backoff is the only safety net until `claim_shipments_to_poll`'s polling fallback catches up |
| **messaging** | Every other context keeps emitting its own events; they queue in messaging's `app.inbox` (no loss) | New conversations/messages, the real-time hub (WebSocket/SSE), all notification *delivery* (rows queue in `notifications` with `delivery_status=pending` once messaging recovers) | Notifications are produced by consumers inside messaging reacting to other services' events — if messaging itself is down, those events simply wait |
| **presence** | Nothing else calls presence synchronously (no gRPC into it anywhere in `c4-diagrams.md`) — zero blast radius on other contexts | Public profile pages (`/b/{slug}`), review submission, moderation | Presence is a leaf in the context map by design (§3.4 "reviews" is the only flow it participates in, and only as a consumer) |
| **RabbitMQ (broker)** | Every service's own direct read/write API keeps working for anything not requiring a *fresh* cross-service event; each outbox keeps accumulating unpublished rows, replayed once the broker is back | All cross-service propagation pauses cluster-wide — contact/order/score read models everywhere fall behind | This is exactly what "outbox oldest-unpublished age" (must-have alert, Tech Decisions v0.2 §9.4) is for — the signal that this is happening |
| **Valkey** | — | BFF sessions (if held only in Valkey, per Tech Decisions v0.2 §7.3, this breaks the whole user-facing BFF — flagged below as a real single point of failure, not softened); score-lookup single-flight/stampede guard lost (functionally still correct, just more load on scoring's DB) | Worth calling out explicitly: Valkey is drawn as "cache" in `c4-diagrams.md` but for BFF sessions it behaves like a hard dependency, not an optional cache — Phase 5 should confirm whether a degraded-but-logged-out mode is acceptable or whether Valkey needs its own HA story sooner than "cache" implies |
| **One Postgres instance (a single service's DB)** | All *other* services (different DB) fully operational — "database per service" pays for itself exactly here | That one service fully down for both reads and writes (no in-process fallback inside a service for its own DB) | Standard per-service blast-radius containment; no cross-database query exists to even attempt a degraded read |

## What this table does not cover yet

- Partial degradation *within* a service (e.g. the webhook-processing worker down but the API up) — out of
  scope until Phase 5's walking skeleton gives real failure-mode data to design against (Tech Decisions v0.2
  §11 "Resilience: kill a service during a flow and verify degradation, replay and recovery").
- Gateway/BFF themselves being down is total outage by definition, not a degradation case.
